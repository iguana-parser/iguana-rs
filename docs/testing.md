# Testing

Iguana has two kinds of tests:

- Unit and integration tests inside the main crates (`cargo test -p <crate>`).
- Grammar tests under `tests/<name>/`. Each is a workspace member crate that owns a grammar and a generated parser library; the actual test cases live in a shared integration-test binary at the workspace root.

This document covers the grammar test workflow.

## Layout

A grammar test under `tests/<name>/` looks like:

```
tests/mygrammar/
├── mygrammar.iggy     grammar definition
├── tests.rs           test cases (pulled into the unified runner)
├── parse_trees/       golden files (s-expression renderings of parsed input)
├── Cargo.toml         minimal: lib-only, test = false, no [[bin]]
└── src/               generated parser library (regenerated by `test-gen`)
```

`src/` is generated and committed so a fresh checkout builds without running the generator.

The per-grammar crate is *not* itself a test target. `Cargo.toml` has `test = false` on `[lib]` and no `[[bin]]`. Its only role is to expose the parser as a library (e.g. `mygrammar::parse_program`).

All `tests.rs` files are gathered into a single integration-test binary at `tests/grammar_tests.rs` (a target of the workspace-root `iguana-tests` package) via `#[path] mod` declarations:

```rust
// tests/grammar_tests.rs
#[path = "expression/tests.rs"]
mod expression;

#[path = "mygrammar/tests.rs"]
mod mygrammar;

// ...
```

This is what keeps `cargo test --workspace` fast: one test binary instead of one per grammar.

## Running tests

```sh
cargo xtask test                           # full workspace
cargo xtask test mygrammar::               # one grammar's tests
cargo xtask test mygrammar::test_example   # one test
```

`cargo xtask test` shells out to `cargo nextest run --workspace` if `cargo-nextest` is installed, otherwise to `cargo test --workspace`. Extra positional args are forwarded as test-name filters.

## Adding a test

Two commands. `test-new` scaffolds; `test-gen` generates the parser and wires the crate into the runner.

```sh
cargo xtask test-new mygrammar
```

`test-new` creates `tests/mygrammar/`, writes a stub `mygrammar.iggy` (`grammar Mygrammar`), and creates `parse_trees/`. Nothing else: no parser, no `Cargo.toml`, no `tests.rs`, no workspace entry. The crate is "orphaned" until `test-gen` runs.

Edit the grammar to define rules and mark a start nonterminal with `@Start`:

```sh
$EDITOR tests/mygrammar/mygrammar.iggy
cargo xtask test-gen mygrammar
```

`test-gen`:

1. Runs the generator with `--cli=false`, which writes a minimal `Cargo.toml` (lib-only, `iguana-runtime.workspace = true`) on first generation and the lib sources under `src/` every time.
2. Writes `tests.rs` if missing, based on `@Start` annotations in the grammar.
3. Wires the crate into three places:
   - workspace `members` in the root `Cargo.toml`,
   - root `[dev-dependencies]` (so `iguana-tests` can use the parser library),
   - `tests/grammar_tests.rs` (`#[path = "mygrammar/tests.rs"] mod mygrammar;`).

`tests.rs` is generated based on the `@Start` annotations:

- One `@Start`: a single `check(input, test_name)` helper that calls `parse_<startname>(&input, &ctx)`.
- Multiple `@Start`s: one `check_<startname>(input, test_name)` helper per start.
- No `@Start`: `tests.rs` is not created. `test-gen` prints a message and skips the file. Add `@Start` and re-run `test-gen` to scaffold it.

`test-gen` writes `tests.rs` only when it does not already exist. After the first generation the file is hand-maintained; subsequent runs of `test-gen` regenerate the parser but leave `tests.rs` alone. To regenerate the scaffold from the current grammar (for example after changing the start symbol's name), delete `tests.rs` and re-run `test-gen`.

`test-gen-all` walks `tests/` and runs `test-gen` for each crate that has a grammar file.

A scaffolded `tests.rs` for a single-start grammar looks like:

```rust
// To regenerate parser:  cargo xtask test-gen mygrammar
// To update golden files: REGENERATE=1 cargo test -p iguana-tests --test grammar_tests mygrammar::

use mygrammar::{parse_program, parse_tree::to_sexpr};
use iguana_runtime::input::Input;
use iguana_runtime::parse_tree::ParseContext;
use iguana_runtime::testing::{check_golden_file, golden_path};

const GRAMMAR_DIR: &str = concat!(env!("CARGO_MANIFEST_DIR"), "/tests/mygrammar");

fn check(input: &str, test_name: &str) {
    let input = Input::from(input);
    let ctx = ParseContext::new();
    let result = parse_program(&input, &ctx).expect("Parse failed");
    let actual = to_sexpr(result.tree.as_parse_tree());
    check_golden_file(&actual, &golden_path(GRAMMAR_DIR, test_name));
}

#[test]
fn example() {
    // check("input text", "example");
}
```

`GRAMMAR_DIR` exists because the unified runner compiles `tests.rs` as a module of `iguana-tests`, so `env!("CARGO_MANIFEST_DIR")` resolves to the workspace root. Joining `/tests/mygrammar` lands us at the per-grammar directory where `parse_trees/` lives.

`ParseContext` owns the bump arena that holds the parse tree; it must outlive any traversal of the tree.

## Golden files

`check_golden_file` compares actual output against `<GRAMMAR_DIR>/parse_trees/<test_name>.txt`. The first run for a new test has no golden, so write the test, then create the goldens:

```sh
REGENERATE=1 cargo xtask test mygrammar::
```

This writes the missing files. Subsequent runs without `REGENERATE=1` compare actual output against the file and fail on any difference.

Update goldens after intentional grammar changes by re-running with `REGENERATE=1`. Always review the resulting diff before committing; the change should match what you expected to do, line for line.

## Removing a test

```sh
cargo xtask test-rm mygrammar
```

Deletes `tests/mygrammar/` and unwires the three places `test-gen` wired: workspace `members`, root `[dev-dependencies]`, and `tests/grammar_tests.rs`.
