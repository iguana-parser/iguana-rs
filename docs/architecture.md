# Architecture

Iguana is a practical, data-dependent GLL parser generator. It reads an Iggy
grammar and generates a Rust parser crate. The generated crate contains
grammar-specific parser and parse-tree code and depends on `iguana-runtime` for
the GLL data structures and algorithms shared by every parser.

## Repository map

### Rust crates

| Crate | Role | Direct internal dependencies |
|---|---|---|
| `iguana-runtime` | Shared parser runtime. | None. |
| `iggy` | Parser for the Iggy grammar language, generated from `iggy/iggy.iggy`. The package publishes as `iguana-iggy`, while its library target remains `iggy`. | `iguana-runtime`. |
| `iguana-compiler` | Grammar validation, analysis, transformation, and Rust code generation. | `iggy`, `iguana-runtime`. |
| `iguana` | Command-line interface for scaffolding projects, generating parsers, and serving WebAssembly bundles. | `iguana-compiler`. |
| `iguana-lsp` | Language server and reusable grammar-analysis functions. | `iggy`, `iguana-compiler`, `iguana-runtime`. |
| `xtask` | Repository build, regeneration, and test workflows. | `iguana-compiler`. |

The workspace root also defines the `iguana-tests` integration-test crate.
Each directory under `tests/` is a generated parser crate for one grammar and
depends on `iguana-runtime`.

### Applications and web packages

| Directory | Role |
|---|---|
| `terrarium` | Tauri application for grammar editing, parser runs, and trace replay. Its Rust backend is a separate workspace under `terrarium/src-tauri`. |
| `editors/vscode` | VS Code extension that launches `iguana-lsp`. |
| `web-ui` | Shared Svelte components, backend interfaces, and parse-tree graph code. |
| `web-viewer` | Static app that runs one generated WebAssembly parser in the browser. |
| `design-viewer` | Static read-only Iggy editor backed by `iguana-lsp` compiled to WebAssembly. |
| `tree-widget` | Plain TypeScript entry point for embedding the parse-tree graph in static pages. |

The repository root is an npm workspace for `web-ui`, `web-viewer`,
`design-viewer`, `terrarium`, and `tree-widget`. The VS Code extension keeps a
separate npm installation under `editors/vscode`.

Terrarium, the two viewers, and the tree widget reuse `web-ui`. `web-viewer`
loads the wrapper generated by `iguana generate --wasm`. `design-viewer`
instead loads the grammar-independent WebAssembly wrapper under
`iguana-lsp/wasm`.

## Bootstrapping

The source-level relationship between `iguana` and `iggy` is circular. Iguana
uses `iggy` to read grammar files, while the committed `iggy` sources were
generated by an earlier Iguana build. The bootstrap workflow is run twice; the
second run must reproduce its output exactly. See the [development
guide](development.md#bootstrapping).

## Generation pipeline

The compiler processes a grammar in six ordered phases:

1. **Identifier resolution.** References are connected to their definitions.
2. **Exact keyword matching.** Exact-keyword constructs are converted to their
   grammar-level restrictions.
3. **EBNF expansion.** Groups, optionals, repetitions, and separated lists are
   converted to derived BNF rules.
4. **Exclusion desugaring.** Alternative exclusions are encoded into the
   grammar.
5. **Precedence desugaring.** Priorities and associativity are encoded as
   data-dependent rules.
6. **Layout insertion.** Layout references are inserted into syntax rules, and
   wrapper rules provide the parser entry points.

The generator then writes the grammar-specific crate:

```text
src/grammar_data.rs    terminals, nonterminals, slots, and analysis tables
src/parser.rs          parse functions and parser state
src/parse_tree.rs      typed parse-tree definitions and construction
src/scanner.rs         scanner code for lexical rules
src/types.rs           types shared by the generated modules
src/lib.rs             public API and re-exports
src/main.rs            CLI binary for the generated parser when enabled
Cargo.toml             crate scaffolding
```

The six library modules are rewritten on each generation. `src/main.rs` is
rewritten when CLI scaffolding is enabled; generation without a CLI neither
creates nor removes it. `Cargo.toml` is created when missing and then
preserved, so local dependency or package changes survive regeneration.
`--force` replaces it with the current scaffold.
The generator does not create or modify license or notice files. Users supply
any such files required for their generated project.

The modules under `iguana-compiler/src/generator/` produce these files.
`post_process.rs` converts comment placeholders to Rust comments and inserts
blank lines before item-level definitions.

## Runtime and parse trees

`iguana-runtime` implements input handling, descriptors, the graph-structured
stack (GSS), the shared packed parse forest (SPPF), scanner support, and generic
parse-tree traversal and rendering. The generated crate supplies the
grammar-specific parser functions, node types, and parse-tree builder.

Most runtime operations are on parser hot paths. New allocations, hashing, or
trait dispatch in the runtime therefore require measurement and justification.

## Tooling

The standalone language server wraps stateless `iguana-lsp` analysis functions
in LSP protocol handlers. Terrarium calls the same functions through Tauri
commands, and the design viewer calls their WebAssembly exports in the browser.

Terrarium runs generated parsers as subprocesses rather than linking them as
libraries. It communicates with each parser through command-line flags and
temporary JSON files for parse trees, SPPF and GSS graphs, timings, statistics,
and trace data.
