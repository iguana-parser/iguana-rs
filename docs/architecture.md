# Architecture

Iguana is a data-dependent GLL parser generator. The generator takes an iggy grammar and emits a self-contained Rust crate. Generated parsers link against `iguana-runtime`, which provides the GLL machinery shared by every output.

## Repository layout

```
iguana-rs/
├── iguana/              # Command-line interface (the `iguana` binary)
├── iguana-compiler/     # Parser generator (grammar IR, analysis, codegen)
├── iguana-runtime/      # Runtime library for generated parsers
├── iggy/                # Generated parser for the iggy grammar definition language
├── iguana-lsp/          # Language server for iggy grammars
├── terrarium/           # Grammar debugging tool (Tauri app)
├── web-ui/              # Shared parse-view renderer (npm package)
├── web-viewer/          # Static web viewer for a wasm-compiled parser
├── design-viewer/       # Read-only grammar design view for the website
├── tree-widget/         # Embeddable parse-tree widget for the website docs
├── editors/vscode/      # VS Code extension
├── xtask/               # Build and workflow tasks (`cargo xtask`)
└── tests/               # Grammar test crates
```

## Crates

| Crate | Role |
|-------|------|
| `iguana-runtime` | Runtime library shared by every generated parser. No internal dependencies. |
| `iggy` | Parser for the iggy grammar syntax, generated by iguana from `iggy/iggy.iggy`. Publishes on crates.io as `iguana-iggy` (the library target stays `iggy`). |
| `iguana-compiler` | Parser generator: grammar IR, analysis, transformations, and code generation. |
| `iguana` | Command-line interface. Builds the `iguana` binary on top of `iguana-compiler`. |
| `iguana-lsp` | Language server for iggy grammars. |
| `terrarium` | Tauri-based grammar debugging tool. Separate workspace at `terrarium/src-tauri`. |
| `editors/vscode` | VS Code extension (TypeScript, not a Cargo crate). Launches `iguana-lsp`. |
| `xtask` | Build and workflow tasks. |
| `tests/<name>` | One workspace member per grammar test. |

## Web packages

The repository root is also an npm workspace. The `web-ui` package holds the shared TypeScript/Svelte components, and the other packages (and terrarium) each mount them in a different host, so there is a single renderer to maintain.

| Package | Role |
|---------|------|
| `web-ui` | Shared web UI components: the parse-view renderer (tree, graph, and s-expression views over a parse tree, driven by a pluggable parser backend) and the read-only design view. |
| `web-viewer` | Static web app that loads a wasm-compiled parser, parses input in the browser, and mounts the parse view on the result. No server and no Tauri. |
| `design-viewer` | Static web app that mounts the read-only design view (Monaco with the iggy LSP compiled to wasm) over a grammar. The website's grammar pages embed it. |
| `tree-widget` | Embeddable widget that renders a printed s-expression as an interactive parse-tree graph. The website's docs embed it for parse-tree examples. |

The web viewer's build output is committed at `iguana/viewer-dist` and embedded into the `iguana` binary, so `iguana try` works without npm and the published crate ships the viewer. `cargo xtask install` rebuilds the viewer from source before building the binary; see [development.md](development.md).

## Dependency graph

```
iguana-runtime  (no internal deps)
       ▲
     iggy   (depends on runtime)
       ▲
iguana-compiler  (depends on runtime + iggy)
       ▲
 iguana / iguana-lsp  (depend on iguana-compiler)
       ▲
   terrarium  (depends on runtime + iguana-lsp)
```

On the JavaScript side, `terrarium`, `web-viewer`, `design-viewer`, and `tree-widget` all depend on `web-ui`. `web-viewer` additionally drives the wasm module that `iguana generate --wasm` produces, and `design-viewer` drives the `iguana-lsp` wasm module.

The relationship between `iguana` and `iggy` is circular at the source level: iguana parses iggy grammar files using `iggy`, and `iggy` itself was generated by an earlier build of iguana. The `bootstrap` xtask keeps the committed iggy parser in sync with `iggy/iggy.iggy`. See [development.md](development.md#bootstrapping).

## Generation pipeline

The generator turns a `.iggy` file into a parser crate. The pipeline lives in `iguana-compiler/src/generator/` and produces:

```
src/grammar_data.rs    static tables: terminals, nonterminals, slots, first/follow/prediction sets
src/parser.rs          parse functions, one per nonterminal
src/parse_tree.rs      parse tree types and the tree builder
src/scanner.rs         scanner (when @Regex rules are used)
src/types.rs           shared types across modules
src/lib.rs             public API and re-exports
src/main.rs            CLI binary for the generated parser
Cargo.toml             scaffolding: written when missing, preserved after
```

Every file under `src/` is rewritten on each generation, `main.rs` included. Cargo.toml is the one scaffolding file: it is preserved once it exists, so hand edits (a path dependency on the runtime, extra features) survive regeneration, and `--force` resets it to the template.

Each output file is produced by a dedicated `*_gen.rs` module. After generation, `post_process.rs` rewrites `#[comment = "..."]` into `//` and `#[doc = "..."]` into `///`, and inserts blank lines before item-level definitions for readability.

## Runtime

`iguana-runtime` hosts the parsing infrastructure: descriptors (work items in the GLL worklist), the graph-structured stack (GSS), the shared packed parse forest (SPPF), input handling, and the parse-tree builder. The runtime is performance-critical; allocations and trait dispatch on hot paths need justification.

## Tooling

`iguana-lsp` and `terrarium` share a set of stateless analysis functions for highlighting, formatting, symbols, and diagnostics. The LSP server wraps them in protocol handlers; terrarium calls them directly through Tauri commands. Terrarium also runs generated parsers as subprocesses (not as library calls) and communicates with them through CLI flags and JSON temp files.
